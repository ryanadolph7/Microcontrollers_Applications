# C coding standard 

This document provides some guidance on code formatting, documentation, modularity, and best practices.

To see categories and short descriptions of how your code will be graded, see the grading rubrics associated with the "code" assignments in Canvas. When a section of this document prescribes what is expected for part of the grading rubric, that will be indicated.


## Comments and documentation

> [!IMPORTANT]
> You will be graded on your adherence to the Doxygen comment standards laid out in this section.

Comments are generally good, but bad comments can be worse than no comment at all. In general, comments should not explain how your code works. If the code itself is not clear, you should rewrite the code. Comments should explain the *intention* of the code, e.g., "what" and "why". Comments that simply duplicate what the code already says are bad comments.

[This stackoverflow post has some thoughts on writing good comments](https://stackoverflow.blog/2021/12/23/best-practices-for-writing-code-comments/).

We'll use [Doxygen](https://doxygen.nl/index.html) comments to document our files, functions, structs, etc. There are no special formatting guidelines for comments that aren't intended to be part of autogenerated documentation. 

This guide uses Javadoc-style doxygen comment blocks:
```c
/**
 * This is a Javadoc style comment block.
 *
 * The comment block starts with two *'s. The *'s on intermediate lines are
 * aligned with the first *. The intermediate *'s are optional, but this style
 * is my personal preference. The ending * is also aligned with the first *,
 * which is indented by one space from the current indentation level.
 */
 ```

### File header documentation
The file header should include a `@file` command, a brief description, and an optional extended description.
```c
/**
 * @file
 * @brief A brief description of the module's purpose.
 *
 * An optional extended description of the module.
 */
```

### Function documentation

```c
/**
 * Brief description of function.
 *
 * A longer description, with more discussion of the function 
 * that might be useful to those using or modifying it. 
 *
 * @param: param1 Describe the first argument.
 * @param: param2 Describe the second argument.
 *
 * @return: If the function has a return value, describe it here.
 */
 uint16_t some_function(int param1, int8_t param2)
```


### Struct and enum documentation

Struct and enum members should be documented above the members. Note that the comments still use two *'s.

```c
/**
 * A brief description of the struct
 *
 * An optional extended description
 */
struct foo
{
    /** Description of bar field */
    uint8_t bar

    /** Description of baz field */
    bool baz
}
```




## Code organization

> [!IMPORTANT]
> Organizing your code into modules and using header files is part of the grading rubric!

All modules should have an associated header file that has a `.h` file extension. `main.c` should be not have a `main.h` header.

### Include guards
Header files should have [include guards](https://en.wikipedia.org/wiki/Include_guard) to prevent multiple inclusion.

`module_name.h`:
```c
#ifdef MODULE_NAME_H
#define MODULE_NAME_H

// ... file content

#endif // MODULE_NAME_H
```

## Naming Conventions

The following naming conventions are my personal preference for C code. You can choose whatever standard naming conventions you like, but please be consistent within your group. I suggest either `snake_case` or `camelCase` for everything except constants, which are typically `ALL_CAPS`.

> [!IMPORTANT]
> Inconsistent naming conventions will be penalized in the grading rubric.

### Filenames
File names should be `snake_case` or `kebab-case`

### Constants
Constants should be `ALL_CAPS`.

### Variables
Variables should be `snake_case`, as this is the most common convention in C.

### Functions
Function names should be `snake_case`.


## Formatting

> [!IMPORTANT]
> Inconsistent formatting will be penalized in the grading rubric.

You are free to use your preferred formatting conventions (e.g., brace placement, indentation, etc.), so long as the convention is standard and not something silly and unreadable. Just be consistent within your group.

### Brace placement

See the [Indentation style Wikipedia article](https://en.wikipedia.org/wiki/Indentation_style) for an overview of different brace placement styles. Please choose one and be consistent.


### Trevor's preferences

The following sections provide a few brief examples of my coding preferences along with some explanations. Again, you aren't required to follow these, but you do need to be consistent within your group.

#### Brace placement

My preferences, in no particular order, are the following:
- Allman (all braces on separate lines)
    ```c
    while (x == y)
    {
        foo();
        bar();
    }
    ```
- K&R (first brace on same line)
    ```c
    while (x == y) {
        foo();
        bar();
    }
    ```
    - Technically, K&R puts the first brace on a new line for functions, which I find inconsistent...

I find most of the other styles mentioned in the Wikipedia article to be absurd...

#### Indentation
- Use 4 spaces for indentations. 
- Use spaces instead of hard-tabs. Set up your editor to use soft-tabs.

Using spaces for indentation assures that your code formatting is consistent regardless of where or how it is being viewed. There's nothing worse than having inconsistent indentation because spaces and tabs have both been used...


#### Line Length

Lines should be less than 120 characters long. This is a soft limit, rather than an absolute hard limit.

If a line is longer than 120 characters, that could indicate some design problems, e.g.,
- your code is nested too deep
- you are using excessively long variable names (descriptive names are good, but they can be too long...)


#### One-line if statements

Brackets should always be used for if statements, even if the body only has one line.

Do this
```c
if (x > 0)
{
    printf("x is positive\n");
}
```

not this
```c
if (x > 0)
    printf("x is positive\n");
```

The reason is that if you need to add more lines to the if statement's body, you will then need to add braces. You might forget to add braces, which will result in a bug because every statement after the first will not be part of if statement's body.

## Coding practices

This section provides guidance on what I'm looking for in the "code quality" section of the rubric.

### Descriptive names

Good variable and function names makes code easier to read and understand. Good names concisely describe the concept the identifier represents. Good names reduce the need for comments (especially comments that explain what a variable is for---the variable name should do that!).

- Avoid generic names (`tmp`, `tmp2`, `foo`)
- Generally avoid single-letter variable names except where the context is clear (e.g., `i` as a loop index, although you can also use more descriptive loop index names).

The following examples and ideas are taken from [Naming Things: The Hardest Problem in Software Engineering by Tom Benner](https://www.namingthings.co/).

#### Parts of speech to use for different identifier types

| Identifier type | Parts of speech                                             | Examples                             |
|-----------------|-------------------------------------------------------------|--------------------------------------|
| Variables       | Nouns, noun phrases, or linking verb and subject complement | `name`, `birth_date`, `is_valid`     |
| Functions       | Verbs, verb phrases, or linking verb and subject complement | `validate`, `delete_all`, `is_valid` |

#### Variables

Variables typically represent objects and values, so they should typically have names that are nouns or noun phrases. One exception to this is booleans, which should be named using a linking verb and subject complement.

Rules:
- Omit metadata
- Omit unnecessary words
- Avoid unconventional single-letter names
- Include units in measurements

##### Booleans

Boolean names should typically be a linking verb and subject complement (e.g., `is_complete`, `has_admin_access`).

Booleans should always use a positive name since negatively-named booleans easily cause confusing double negatives.

**Example**:

Bad:
```
if !is_invalid:
    user.save
```
Good:
```
if is_valid:
    user.save
```

#### Methods

Method names should typically be verbs or verb phrases. Methods that return booleans should be named using a linking verb and subject complement.

The name should describe what the method does. If a method does multiple things, the author should carefully consider the single-responsibility principle and consider refactoring the method into multiple methods.

#### Abbreviations

Abbreviations, including truncations (e.g., "org" for "organization") and acronyms (e.g., "AP" for "accounts payable"), are less likely to be understandable than the full term that they abbreviate. Consequently, abbreviations should be kept to a minimum. Widely known abbreviations, like "URL", "DNS", and "ID", are exceptions.

### Hard-coded values / magic numbers

Hard-coded values / [magic numbers](https://en.wikipedia.org/wiki/Magic_number_(programming)) fail to explain the code's intent. If the same hard-coded value is used in more than place, maintenance becomes harder because the value needs to be replaced in multiple locations; failure to replace every instance can lead to bugs.

Magic numbers should be replaced with named constants. Using descriptively named constants can make the code's intent more clear. Named constants also solve the maintenance problem described earlier.

### Commented-out code

Commented-out code distracts the reader. If the code is commented-out, it is likely not needed. If the code is not needed, it should be deleted. Version control preserves history, so you can always go back and see the deleted code if needed.

### Code duplication

Unnecessarily duplicated code can lead to maintenance overhead and an increased chance of bugs. When a duplicated piece of code needs to be updated, one must remember to update it in all locations; failing to update all locations can lead to bugs.

When duplicated code can easily be refactored into a function, you should create a function. A general rule of thumb is if you're using the code in three or more places, you should consider turning it into a function.

However, there are always tradeoffs. If the code fragment has differences each time it is used, the cost of creating an abstraction that handles all cases may not be worthwhile. This must be evaluated on a case-by-case basis, though preference should be given towards having a single source of truth.

## Extras

### Autoformatting code

CCS has a clangd extension installed by default that can format code. A `.clang-format` file is included in your repositories that is configured for my preferences. You can change the file to match your preferences.

You may format your code in CSS by running "Format document" or "Format selection" (ctrl+shift+p, then type format).

> [!NOTE]
> You must first download the clangd server (ctrl+shift+p -> clangd: Download language server)

### Linting

`clang-tidy` is included in the clangd extension in CCS. `clang-tidy` will provide suggestions and warnings about common programming errors and bug-prone bug.

There is a `.clang-tidy` file in your repositories that has some checks configured.

Suggestions will automatically show up in CCS in the "problems" tab and as red squiggles in the text editor.
